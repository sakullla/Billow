# TUN 与系统代理独立性修复

## 现场检查

2026-11-17 在本机读取实际内核配置及系统路由：TUN 已启用、auto-route 已启用，公网 IPv4 路由指向 utun4。用 `curl --noproxy '*'` 分别访问 GitHub 与 example.com 均得到 HTTP 200；显式 HTTP 代理方式也得到 200。本次检查没有切换系统代理、TUN 或用户节点。

因此不能把之前一次 GitHub 直连超时当成 TUN 持续失效的证据，也不宣称所有网络场景都已排除问题。

## 已确认的应用问题

- 开启 TUN 成功后，后端用 system_proxy 标志决定 connected，单开 TUN 会被判为未连接。
- 关闭系统代理会把 connected 清零，即使 TUN 仍在工作。
- 连接列表和流量统计以 connected 为条件，因此上述状态错误会导致有效 TUN 会话的数据不显示。
- 首页将 connected=false 当成内核未运行，没有区分「内核仍运行但没有接管流量」。

修复成功启用 TUN 后的连接状态，并让系统代理开关保留 TUN 会话。TUN 开关不修改 OS 系统代理设置；真实内核退出时仍会清除连接状态。Demo 后端与首页显示同步这一语义。

## 验证

回归覆盖单独开启 TUN、系统代理与 TUN 同时开启后只关闭系统代理、再关闭 TUN、TUN-only 连接列表、内核退出，以及首页开关和流量显示。原 TUN-only 用例修复前失败，修复后与完整前后端测试一起验证。
