# T35 — shared userspace L3 stack, WireGuard and OpenVPN data paths

Task T35 (outcomes: shared L3 client stack; WireGuard handshake/data/allowed-ips/
keepalive/MTU/IPv4/IPv6; OpenVPN AEAD/PUSH_REPLY ifconfig/keepalive; both UDP
consumers; bounded concurrency and reclaim; named errors).

The controlled WireGuard peer (`tool/kernel-compat/peers/wireguard-peer/main.go`)
now echoes IPv4 UDP and runs a minimal IPv4 TCP responder (SYN-ACK, data echo,
FIN) inside its fake TUN; it still answers ICMP as before. The peer remains a
fixture built from the locked `metacubex/wireguard-go`; no kernel code is copied
from it.

## What is verified, and what is not

- **Verified end to end**: WireGuard over the locked device for ICMP, UDP and
  TCP; two peers chosen by `allowed-ips`; IPv4. IPv6 and MTU behaviour are
  verified against the independent in-tree peer (`tunnel::tcp_server` and
  `ipstack`), not through the Go WireGuard device.
- **Verified for OpenVPN**: the real control channel, TLS, key-method 2,
  `PUSH_REPLY` parsing, AEAD keepalive decryption, `send_data` acceptance and
  stack construction/local-address wiring against OpenVPN 2.7.9 `--dev null`.
- **Not verified**: delivery of a TCP/UDP payload through a real OpenVPN
  tunnel. `--dev null` discards the IP packets, so this document does not claim
  OpenVPN end-to-end datapath parity. A full test needs a TUN-capable server or
  a userspace OpenVPN peer that routes packets, neither available in this
  environment.
- **Not implemented (named)**: AmneziaWG, explicit `ip-stack.mode: mips|gvisor`,
  `ip-stack.congestion-controller`, stack `remote-dns-resolve`/`dns`, WireGuard
  endpoint refresh, `tls-auth`/`tls-crypt`, CBC data ciphers, compression.
- **Option matrix**: no row changes. `ip-stack` (no value) stays an accepted
  no-op; the enabled `ip-stack.mode` row stays `rust=reject mihomo=accept`
  because `mips`/`gvisor` remain unimplemented — the rejection reason now names
  smoltcp instead of T6/T7. `udp_enabled` semantics changed for
  `openvpn`/`wireguard` but no matrix row encodes that method.

## Residual risks

- smoltcp's TCP congestion control is its own (no Reno/BBR parity with the
  pinned mips/gVisor stacks); throughput/behaviour parity is not claimed.
- The stack's poll cadence is 2 ms with a 4 ms egress dispatch for WireGuard;
  this bounds latency but is not a tuned data plane.
- The OpenVPN actor holds the blocking link on one OS thread and polls with a
  10 ms receive timeout; `ping`/`ping-restart` are parsed but not enforced as
  timers here.
- WireGuard handshakes every configured peer eagerly when the stack is built.
  One unreachable peer fails stack creation even when the target would use a
  different peer; the pinned device connects lazily per peer. Multi-peer
  selection itself is verified with two live peers.
- `resolve_all` for the destination also sees the proxy-server DNS task-local
  scope when the caller installed one; this matches the task recipe but means a
  destination name can use `proxy-server-nameserver` on that path.
