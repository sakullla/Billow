# T35 — shared userspace L3 stack, WireGuard and OpenVPN data paths

Task T35 (outcomes: shared L3 client stack; WireGuard handshake/data/allowed-ips/
keepalive/MTU/IPv4/IPv6; OpenVPN AEAD/PUSH_REPLY ifconfig/keepalive; both UDP
consumers; bounded concurrency and reclaim; named errors).

## T35-A2 repair summary

- **P1-1 lazy WireGuard peers / lock scope**: no eager handshake; the first
  packet or `dial`'s `ensure_peer` starts one peer. A failed peer backs off and
  drops only its own packets; `dial` never falls back and reports the resolved
  endpoint. The registry lock covers only double-check lookup/publish; endpoint
  resolution, socket binding, the OpenVPN thread handoff and its one-shot wait
  are outside it.
- **P1-2 TCP capacity/liveness**: 16 concurrent sockets with a 64-dial bounded
  admission queue (wait within the dial timeout, `TooManyWaiters`/`OutOfMemory`
  beyond), smoltcp 60 s timeout and 30 s keepalive; tests cover slot release,
  queue cap and dead-peer reclaim.
- **T35-A3 P3 cleanups**: forget hooks are documented API-only; the poller
  stop check is one locked decision followed by a recheck and a post-admission
  poller restart; WireGuard keepalives touch the stack; TCP admission timeout
  names 16 slots and the wait duration (waiters are wake-all, bounded, not
  strict FIFO); UDP outside `allowed-ips` is a named `NoRoute`; multi-segment
  PUSH_REPLY is accumulated; stale evidence contradictions (10 ms vs 50 ms,
  4 ms vs 2 ms, ping not enforced vs enforced) are removed.
- **P1-3 OpenVPN timers**: `ping`/`ping-restart` from PUSH_REPLY or configuration
  drive `last_sent`/`last_inbound`; ping sends keepalives, ping-restart fails the
  stack. `tran-window`/`handshake-timeout`/renegotiation remain unimplemented
  and are recorded, not silently claimed.
- **P3-4/5**: PUSH_REPLY parses `dhcp-option DNS`, `block-ipv6`,
  `push-continuation`, `auth-token` (recognized) and ping values; replayed data
  packet ids are dropped with `continue`; the blocking link read is the named
  50 ms `LINK_READ_TIMEOUT`.
- **P3-6/7**: strong registries with `MAX_STACKS = 64`, 5 s idle sweep and
  explicit forget hooks (API-only, not engine-wired); per-stack memory table (1 MiB TCP + 4 MiB UDP + device
  queues + 128 KiB per WireGuard peer) and the 64-stack ceiling are documented.
- **P3-8**: OpenVPN `proto: tcp` frames are buffered (`FrameBuffer`) so a read
  timeout cannot lose a half frame; a real OpenVPN 2.7.9 `tcp4-server` case
  passes. That run found packet-id 0 rejected by the server; the first client
  data packet is now id 1.

## What is verified, and what is not

- **Verified end to end**: WireGuard over the locked device for ICMP, UDP and
  TCP; two peers chosen by `allowed-ips`; one live peer with one dead endpoint
  (live dial/UDP still work, dead-peer dial fails by name, no fallback); IPv4.
  IPv6 and MTU behaviour are verified against the independent in-tree peer
  (`tunnel::tcp_server` and `ipstack`), not through the Go WireGuard device.
- **Verified for OpenVPN, control plane**: the real control channel over UDP
  **and TCP framing**, TLS, key-method 2, `PUSH_REPLY` parsing, AEAD keepalive
  decryption, `send_data` acceptance and stack construction/local-address
  wiring against OpenVPN 2.7.9 `--dev null`. The TCP case also proves the
  length-prefix buffer survives a read timeout; the server rejected packet-id
  0, which fixed the first data packet id to 1.
- **Verified for OpenVPN, real payload (T35-A3)**: the Docker peer runs a real
  `--dev tun0` server (Ubuntu 22.04 OpenVPN) with `10.8.0.1/24`; the Rust L3
  stack got local `10.8.0.2` and completed **TCP echo** (`hello-ovpn`) and
  **UDP echo** (`udp-ovpn` from `10.8.0.1:7778`) through the tunnel. This is
  real IP payload delivery, not `--dev null`. The container is removed by a
  Drop guard after the assertions.
- **Not verified**: OpenVPN UDP **control** transport against a real TUN
  (Docker Desktop UDP port mapping is unreliable on macOS); multi-segment
  PUSH_REPLY is implemented and unit-tested but no real server in this
  environment forces it; WireGuard IPv6 through the Go fixture (its fake TUN is
  IPv4-only, IPv6 is covered by the independent in-memory peer).
- **Not implemented (named)**: AmneziaWG, explicit `ip-stack.mode: mips|gvisor`,
  `ip-stack.congestion-controller`, stack `remote-dns-resolve`/`dns`, WireGuard
  endpoint refresh, `tls-auth`/`tls-crypt`, CBC data ciphers, compression,
  OpenVPN renegotiation (`reneg-sec`) and `tran-window`/`handshake-timeout`
  semantics. The latter two are accepted at load but not used: `handshake-timeout`
  is not a separate timer (the dial timeout bounds the control handshake) and
  `tran-window` is not enforced. `auth-token`/`push-continuation` are recognized
  and recorded, not used.
- **Option matrix**: no row changes. `ip-stack` (no value) stays an accepted
  no-op; the enabled `ip-stack.mode` row stays `rust=reject mihomo=accept`
  because `mips`/`gvisor` remain unimplemented — the rejection reason now names
  smoltcp instead of T6/T7. `udp_enabled` semantics changed for
  `openvpn`/`wireguard` but no matrix row encodes that method.

## Per-stack memory (T35-A2, R3/R4)

Worst case for one stack (mtu 1500, P WireGuard peers):

| part | bytes |
| --- | --- |
| TCP sockets | 16 × 2 × 32 KiB = **1,048,576** |
| UDP sockets | 32 × 2 × 32 × 2048 = **4,194,304** |
| device RX+TX queues | 2 × 256 × 1500 = **768,000** (at mtu 1408: 720,896) |
| WireGuard peer actor + tunnel scratch | P × (64 KiB + 64 KiB) = **131,072 × P** |
| sockets/interface/maps/interfaces | < 64 KiB |

So one stack with one peer is ≈ **5.9 MiB** (≈ 5.8 MiB at mtu 1408), plus
125 KiB for every additional WireGuard peer. `MAX_STACKS = 64` gives a
worst-case active-stack ceiling of roughly **378 MiB + 8 MiB × P** (P peers per
stack), before the separate `tunnel/udp` per-flow 64 KiB receive buffers. The
TCP admission queue adds up to 64 waiting dial futures (no per-waiter data
buffer). UDP datagrams above 2048 bytes are refused even if the MTU is larger,
which is what keeps the 4 MiB UDP bound exact.

## Residual risks

- smoltcp's TCP congestion control is its own (no Reno/BBR parity with the
  pinned mips/gVisor stacks); throughput/behaviour parity is not claimed.
- The stack poller runs at 500 Hz (`POLL_INTERVAL` 2 ms); WireGuard egress
  dispatch also polls at 500 Hz, and OpenVPN's blocking actor reads with a
  50 ms link timeout (`LINK_READ_TIMEOUT`) inside a 10 ms poll call.
- WireGuard egress dispatch and the stack poller both run at 500 Hz (2 ms);
  this bounds latency but is not a tuned data plane.
- WireGuard now matches the pinned lazy behaviour: stack creation only resolves
  peers and binds sockets; each peer handshakes on first use. A dead peer keeps
  retrying at most once per second after a failure; its packets are dropped
  until then, without affecting other peers.
- TCP admission waiters are woken wake-all and re-check the slot; the queue is
  bounded at 64 but not strictly FIFO, so a newly arriving dial can win a slot
  before an older waiter. The timeout error names 16 slots and the wait
  duration.
- The strong registries cap active stacks at `MAX_STACKS = 64`; a configuration
  that activates more proxies at once is refused by name. Idle stacks are
  reaped after 60 s (5 s sweep). `l3::forget` / `wireguard::forget` /
  `openvpn::forget` exist as API hooks but are not wired into engine
  reload/close, so do not treat them as an active stop path yet.
- `resolve_all` for the destination also sees the proxy-server DNS task-local
  scope when the caller installed one; this matches the task recipe but means a
  destination name can use `proxy-server-nameserver` on that path.
